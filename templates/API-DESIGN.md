# API pumba для агентов и самописные скрипты: дизайн

Статус: проект, код не написан. Цель — чтобы драйвер `pumba-task` и исполнители тратили контекст на работу, а не на бухгалтерию доски. Два механизма: детерминированные команды того же бинарника (`pumba <команда>`) и скрипты, которые агенты пишут себе сами в `.pumba/scripts/` и обновляют, когда меняются правила доски.

Оценки токенов ниже — расчёт по размерам файлов (3,3 байта на токен), а не замер. Замер — пакет WP7.

## 1. Измерение

ccwatch можно использовать как необязательный способ измерить экономию: прогнать им одну и ту же карточку до и после появления API и сравнить число вызовов и размер контекста. Ни команды, ни скрипты, ни шаблоны от него не зависят.

## 2. Повторяющиеся действия драйвера и их цена

Главная цена — не вывод, а число вызовов: каждый вызов инструмента — запрос, который перечитывает весь контекст. Драйвер к середине карточки держит 60–150k. Второе — большие выводы, которые остаются в контексте.

Размеры: SKILL.md `pumba-task` — 28,6 КБ (~8,7k ток.); правила колонок по умолчанию — 6,5 КБ (~2k), из них «В работе» 2,2 КБ (~680); `board.json` по умолчанию ~11 КБ (~3,4k); AGENTS.md: протокол ~1,1k, правила проекта ~0,5k, индекс ~40 ток. на карточку (в `sandbox` 84 карточки, 18,4 КБ, ~5,6k).

| # | действие (раздел скилла) | вручную: вызовы / токенов в контекст | через API |
|---|---|---|---|
| 1 | найти корень, прочитать AGENTS.md и board.json (§0, §1.4) | 3 / 7–11k | `brief`: 1 / 0,4–1,2k |
| 2 | нормализовать id, найти похожие при промахе (§1.1) | 1–2 / 0,3–0,5k | внутри `brief` (код 3 + похожие) |
| 3 | `deleted`, зависимости: прочитать каждую, сверить с последней колонкой (§1.2–1.3) | 1+N / 0,3k×N | внутри `brief` (коды 4, 5) |
| 4 | на каждом круге перечитать карточку и колонку (§2.1–2.2), 3–5 кругов | 1–2 на круг / 0,3–1k | `brief --known`: 1 / ≤150 |
| 5 | перенос: Read + Edit строки `column:`, риск опечатки в id (§2.8, §7) | 1–2 / 0,1–0,5k | `move`: 1 / ~30 |
| 6 | заметка: `date` + Read хвоста + Edit (§7) | 2–3 / 0,2–0,6k | `move --note` или `note`: 0–1 / ~20 |
| 7 | новая карточка: Glob id, Grep названий, Grep `order`/`column`, board.json, Write (new-card §2–5) | 4–6 / 3–6k | `new`: 1 / ~30 |
| 8 | разблокированные карточки для отчёта (§6) | 2–4 / 0,5–2k | `unblocks`: 1 / ≤100 |
| 9 | каждый субагент читает AGENTS.md ради «Правил проекта» (агенты, «Что прочитать») | 5–7 чтений × 3,5–7k в свежие контексты | `rules` в задании: 0 / ≤600 |
| 10 | git вокруг ролей: `status`, ветка, `rev-parse` (§4) | 3–5 / 0,2–2k | `branch-name` + скрипт |
| 11 | хеши тестов до и после исполнителя (§3) | 2 / 0,1k + сравнение «в уме» | скрипт (v2: `hashes`) |
| 12 | коммиттер: AGENTS.md, ветка, пустой индекс, status, add, сверка, log (committer 1–5) | 7–8 на haiku / 4–8k | v2 `commit-prep`: 1 + `git commit` |
| 13 | проверки проекта с хвостом вывода (§2.5, §3) | 1–3 / 0,5–5k | скрипт `.pumba/scripts/` (не API: команды проектные) |

Итог на одну задачу по колонкам по умолчанию: вручную ~30 служебных вызовов драйвера (×80k контекста ≈ 2,4M чтения кэша) и ~10k постоянного груза в контексте (×100 запросов ≈ 1M); через API ~10 вызовов (≈0,8M) и ~1k груза (≈0,1M). Субагенты дополнительно экономят 20–50k входа на чтениях AGENTS.md.

## 3. API: команды `pumba`

### 3.1 Общие правила

- Бинарник тот же: `pumba` (крейт `pumba-board`, `[[bin]] name = "pumba"` в `Cargo.toml`). Подкоманды разбираются в `main.rs` рядом с `init`/`install`/`install-claude`. Подкоманда главнее пути: каталог проекта с именем `list` открывается как `pumba ./list`.
- Не интерактивны: TUI не запускают, ничего не спрашивают, stdin читают только при `--body -`.
- Корень: `--root <путь>` или поиск вверх от текущей папки (`Store::find`).
- Вывод: компактный текст для агента; `--json` — один JSON-объект в stdout. Ошибки — одна строка в stderr: `pumba: <что> (<код>)`. Цвета нет.
- Запись — только через ядро (§3.4): свежее чтение, сверка перед записью, атомарная запись, регенерация AGENTS.md.
- Идемпотентность: повтор того же вызова не меняет файлы и выходит с кодом 0 (`move` в ту же колонку, `note` с тем же текстом, что последняя строка).
- Ручной режим доски («Обновление доски: Вручную»): команды записи отказываются с кодом 7 и печатают готовую фразу-предложение. `--user-approved` — только после явного «да» пользователя в этой беседе.

Коды выхода (общие для всех команд):

| код | смысл |
|---|---|
| 0 | успех (в том числе «уже так») |
| 1 | ошибка ввода-вывода |
| 2 | неверные аргументы |
| 3 | нет карточки или колонки; у колонки нет `next` (stdout: похожие id или список колонок) |
| 4 | карточка в корзине |
| 5 | карточка заблокирована зависимостями (stdout: «T-003 — «В работе» (`in-progress`)») |
| 6 | конфликт: файл меняли параллельно, 3 попытки не удались, или `--expect-from` не совпал |
| 7 | запрещено правилом доски (ручной режим без `--user-approved`) |
| 8 | скрипт устарел: правила изменились (`scripts check`, `run`) |
| 9 | доски нет или `board.json` не читается (ничего не записано) |
| 10 | возможный дубль названия (`new` без `--allow-dup`) |

### 3.2 Таблица команд

| команда | что делает | вывод (текст) | релиз |
|---|---|---|---|
| `brief <id> [--known <части>] [--body head\|full\|none] [--json]` | всё для шага драйвера: поля карточки, колонка и три части её правила, исполнитель, `next`, завершающая колонка, блокировки, родитель, зависимые, режим доски, метки правил проекта, хеши, последние переносы, тело | ≤150 ток. без текста колонки; + текст колонки дословно; тело `head` ≤40 строк | MVP |
| `move <id> <колонка\|next> [--expect-from <кол>] [--note "текст"] [--user-approved]` | меняет `column` и `order` (в конец колонки, как TUI), дописывает заметку ««Откуда» → «Куда»: текст», обновляет AGENTS.md | `T-005: in-progress → review` | MVP |
| `note <id> "текст" [--user-approved]` | дописывает строку в `## Ход работы` (раздел создаётся в конце тела) | `T-005: заметка добавлена` | MVP |
| `rules [--part <id>…] [--json]` | выбранные «Правила проекта» и «Свои правила» — для заданий субагентам | ≤600 ток. | MVP |
| `unblocks <id> [--json]` | зависимые карточки и их статус: «разблокирована», «ждёт ещё T-006», «разблокируется, когда T-005 дойдёт до «Готово»» | по строке на карточку | MVP |
| `rules-hash [--parts] [--json]` | отпечаток правил (§4.2) | 1 строка; с `--parts` — по строке на часть | MVP |
| `column <col-id> [--json]` | одна колонка: имя, три части, `agent`, `next` | текст колонки | MVP |
| `new --title T [--type task\|epic] [--column] [--parent] [--depends a,b] [--sprint N\|none] [--model] [--effort] [--body-file F\|--body -] [--allow-dup] [--dry-run]` | карточка со следующим id (с учётом корзины), проверки родителя, зависимостей и кругов как в TUI | новый id; при `--dry-run` — id и файл | v2 |
| `list [--column] [--sprint N\|current] [--parent E] [--blocked\|--unblocked] [--deleted] [--json]` | индекс карточек из файлов | `T-005 review s1 dep:T-003 blk:T-007 «Название»` | v2 |
| `branch-name <id> --slug <латиница>` | имя ветки и базовая ветка по правилу «Модель ветвления» | `pumba/T-005-login-form base=main` | v2 |
| `scripts list\|check [<имя>]` | индекс `.pumba/scripts/` из шапок; проверка отпечатков | §4 | v2 |
| `run <имя> [аргументы]` | выполняет рецепт `.pumba/scripts/<имя>.pumba` (§4.3) | вывод шагов, код первого упавшего | v2 |
| `hashes save\|check <id> <файлы>` | хеши файлов тестов в `.pumba/runs/<id>.json`, сверка | `ok` или изменённые файлы | v3 |
| `commit-prep <id> --branch B -- <файлы>` | шаги 2–5 коммиттера: ветка, пустой индекс, фильтр по `git status`, без `.pumba/`, `git add -- …`, сверка; печатает правило «Стиль коммитов» и 5 последних тем | список, исключённые с причиной | v3 |

Что не делаем командой: выбор исхода по «После работы» и выбор исполнителя (это суждение по тексту правила), slug ветки (перевод русского названия), команды проверок проекта (их знает план, а не доска).

### 3.3 Формат `brief`

```
OK T-005 task «Форма входа» sprint=1 model=default effort=default
col=in-progress «В работе» (2/5) agent=pumba-worker next=review «На ревью» last=done
parent=E-002 «Авторизация» in-progress | depends: T-003 done ✓ | dependents: T-007 (ждёт ещё T-006)
board=auto autonomy=ask tests=required commits=conventional branching=per-task merge=squash
hash rules=3f9a1c0b7e21 col:in-progress=8c1d02aa91f0
log: 31.10 14:05 backlog→in-progress; visits in-progress=1
## Перед работой
<before дословно>
## Работа
<rule дословно>
## После работы
<after дословно>
## Тело (12 строк)
<тело>
```

Первая строка — статус: `OK`, `BLOCKED T-004 «В работе» (in-progress)`, `DELETED`, `NO-PIPELINE` (ни у одной колонки нет `agent` и `next`), `UNKNOWN-COLUMN` (колонки из `column:` нет — pumba показывает карточку в первой). Код выхода: 0, 5, 4, 0, 0. `--known col:in-progress=8c1d…` опускает части, хеш которых агент уже видел: на повторных кругах `brief` укладывается в ~150 токенов. Цель «≤400 токенов» выполняется для всего, кроме текста колонки: он — программа шага, и сокращать его нельзя (у «В работе» по умолчанию ~680 токенов, один раз за прогон). `visits` считается по строкам переносов в `## Ход работы` за последние 24 часа — для защиты «третий раз в одной колонке».

### 3.4 Ядро и рефакторинг

Сейчас логика размазана по `App` (`src/app.rs`, 3,5k строк, вместе с состоянием интерфейса): `blockers`, `dependents`, `effective_col`, `epic_progress`, `next_order`, `new_id`, `parse_depends`/`check_cycles`, `merge_external`, `commit` (откат при ошибке, регенерация AGENTS.md). `Store` и `Task::{to_md,from_md,merge_disk}` в `src/model.rs` уже без интерфейса.

План:
1. Новый `src/core.rs`: свободные функции над `(&Config, &[Task])` — `effective_col`, `last_col`, `blockers`, `dependents`, `next_order`, `new_id(tasks, store, kind)`, `check_cycles`, `resolve_column(cfg, "next" | id)`; плюс `Board { store, cfg, tasks, raws }` с `load(root)` и `write(ids, cfg: bool)`.
2. `Board::write` для CLI: перед записью перечитать файл; текст отличается от прочитанного — повторить операцию на свежих данных (до 3 раз), иначе код 6. Запись атомарная: временный файл рядом и `rename` (на Windows `fs::rename` заменяет файл). Затем `write_agents`.
3. `Store::save_task`/`save_config` перевести на атомарную запись — это полезно и TUI: сейчас `fs::write` может отдать TUI полузаписанный файл (он покажет «Не прочитано»).
4. `App` делегирует в `core` однострочными обёртками. Этот шаг откладывается до конца параллельной правки `src/` другим агентом: до него `core` дублирует 5 мелких функций, а тест `core_matches_app` сверяет их на одной доске.

Совместная работа с открытым TUI уже покрыта: TUI раз в тик сверяет `Store::signature` и перечитывает доску; перед своей записью `merge_external` берёт с диска поля, которые TUI не менял (колонку, тело с заметками). CLI сам ничего не кэширует.

Время для заметок: в зависимостях нет местного часового пояса (`fmt_utc` — только UTC). Варианты: `chrono` с `clock` или `--at` от агента. Рекомендация — `chrono`.

Оценка: ядро 1–1,5 дня, чтение 1–1,5, запись 1,5, отпечаток 0,5, скрипты 1–1,5, шаблоны 1–1,5, тесты и замер 1. Всего 7–9 агенто-дней, MVP — ~4.

## 4. Самописные скрипты агентов

### 4.1 Где и что

- Только `.pumba/scripts/`. pumba эту папку не читает при загрузке и не следит за ней (`Store::load_full` читает `tasks/*.md`, `signature` — `board.json` и `tasks/`), так что скрипты не будят TUI.
- Индекс — шапки самих файлов; `pumba scripts list` печатает его. Отдельный индекс-файл не ведём: он расходится с файлами.
- Два вида, по порядку предпочтения:
  1. **Рецепт** `<имя>.pumba` — строки подкоманд `pumba` (без имени программы) и `git` только на чтение. Выполняет `pumba run <имя> <аргументы>`: подстановки `$1…$9`, остановка на первом ненулевом коде. Без оболочки, без труб и перенаправлений, поэтому одинаково работает в PowerShell и sh и безопасен по построению.
  2. **Скрипт на языке проекта** (`.mjs`, `.py`, `.ps1`/`.sh` по проекту) — когда нужна логика: проверки проекта, разбор вывода, хвост лога. Язык — тот, на котором уже есть рантайм в проекте; иначе пара `.sh` + `.ps1`.
- Не скриптовать: разовое действие; решения (куда переносить при замечаниях, какой исполнитель); чтение кода; то, что уже делает одна команда `pumba`.

### 4.2 Отпечаток правил

`pumba rules-hash` — FNV-1a 64 бита своей реализацией (без новых зависимостей, `DefaultHasher` не стабилен между версиями Rust), 12 hex-символов. Части:

| часть | что входит |
|---|---|
| `proto` | версия протокола агентов (константа в коде, +1 при правке протокола AGENTS.md или формата вывода команд) |
| `cols` | порядок id колонок (от него зависит завершающая колонка) |
| `col:<id>` | `id`, `name`, `before`, `rule`, `after`, `agent`, `next` (цвет не входит) |
| `rule:<id>` | выбранное значение и текст выбранного варианта («Стиль коммитов», «Обновление доски», …) |
| `custom` | «Свои правила» |

Общий хеш — от отсортированных хешей частей. Спринт, модели, `tools`, индекс задач не входят. Строка в начале `.pumba/AGENTS.md` (генерирует `agents_md`): `<!-- pumba-rules-hash: 3f9a1c0b7e21 · protocol 1 -->`. Отдельная команда `diff-rules` не нужна: старых текстов нет, а хеши частей уже говорят, что читать заново (`pumba column <id>` или `rules --part <id>`).

### 4.3 Шапка и пример «закрыть карточку»

`.pumba/scripts/close-card.pumba`:

```
# pumba-script: close-card
# purpose: ревью одобрено, коммит сделан: перенести в done с заметкой и показать разблокированные
# usage: pumba run close-card <id> <хеш коммита>
# pumba-rules-hash: 3f9a1c0b7e21
# pumba-parts: col:review=8c1d02aa91f0 col:done=77aa01bc2e10 rule:board=0b3e5f6a7c81 cols=5d0e9a11c2f3
# pumba-protocol: 1
git log --oneline -n 1 $2
move $1 done --expect-from review --note "ревью одобрено, коммит $2"
unblocks $1
```

`pumba scripts check close-card` пересчитывает каждую часть из `pumba-parts`. Совпали — код 0. Не совпали — код 8 и строки `stale close-card: col:review (читай: pumba column review)`. `run` делает ту же проверку сам и устаревший рецепт не запускает. Если пользователь в TUI поменял «После работы» у `review` (например, перед `done` добавил колонку `qa`), рецепт отказывается, а не переносит карточку мимо новой колонки. Скрипт на языке проекта несёт ту же шапку в комментариях и вызывает `pumba scripts check <имя>` первой строкой. Для скриптов проверок добавляется `# pumba-inputs: package.json=<хеш>` — файлы проекта, из которых взяты команды; `scripts check` сверяет и их.

### 4.4 Инструкция агенту (новый раздел скилла и пункт 13 протокола AGENTS.md)

> **Повторяющиеся действия.** Сначала ищи готовую команду: `pumba --help`. Последовательность из двух и больше команд, которую ты выполняешь второй раз за сессию или которая уже нужна была на другой карточке, оформи скриптом в `.pumba/scripts/`: рецептом `<имя>.pumba`, если хватает команд `pumba` и чтения git, иначе — скриптом на языке проекта. В шапке — `pumba-script`, `purpose`, `usage`, `pumba-rules-hash` и `pumba-parts` из `pumba rules-hash --parts` (только части, на которые скрипт опирается). Перед каждым запуском скрипта из `.pumba/scripts/` выполни `pumba scripts check <имя>`. Код 8 — правила изменились с прошлого запуска: прочитай названные части, перепиши скрипт под новые правила и обнови шапку или удали скрипт, если он больше не нужен; только потом запускай. Скрипт не решает за тебя, куда переносить карточку при неудаче, — он лишь выполняет решённое.

Жёсткие правила для скриптов:
- живут только в `.pumba/scripts/`; не меняют `src/`, тесты и `.pumba/tasks/` иначе как через `pumba`; `board.json` и AGENTS.md не меняют вовсе;
- вызывают только `pumba`, git на чтение (`status`, `diff`, `log`, `show`, `rev-parse`, `hash-object`, `merge-base`, `branch --show-current`, `ls-files`) и команды проверок, взятые из плана или манифестов проекта;
- без сети, без установки зависимостей, без `push`, `reset`, `checkout`, `stash`, `rebase`, `--force`, без удаления файлов;
- идемпотентны: повторный запуск с теми же аргументами ничего не портит;
- печатают итог, а не простыню: не больше 40 строк, длинный вывод — во временный файл вне дерева проекта, путь — в выводе;
- субагенты-исполнители скрипты не пишут и не правят: это делает драйвер.

## 5. План работ

### 5.1 Первый релиз (≈80 % экономии)

`brief`, `move` (с `--note`, `--expect-from`, ручным режимом), `note`, `rules`, `unblocks`, `column`, `rules-hash` + строка хеша в AGENTS.md, плюс переписанный скилл `pumba-task` и задания субагентам с блоком «Правила» от `pumba rules`. ## 6. Главные риски

1. **Команды нет или она старая.** Агент работает в среде без `pumba` в PATH или с другой версией, чем шаблоны. Защита: `brief` печатает `api=<версия протокола>`; скилл при коде 127 или неизвестной команде переходит на ручной протокол.
2. **Гонка с TUI и другими агентами.** Защита: сверка перед записью, атомарный `rename`, `--expect-from` у `move`, повтор до 3 раз, затем код 6. Нормализация файла через `Task::to_md` (выбрасывает незнакомые ключи, CRLF → LF) — то же, что делает TUI.
3. **Обход ручного режима.** `--user-approved` агент может поставить сам. Это защищает только правило в скилле, код это не проверит.
4. **Подкоманда против пути.** `pumba list` перестанет открывать папку `list`. Последствие мелкое, указать в USAGE.
5. **Расхождение пяти копий шаблонов.** Правки WP6 делать по списку §5.3 и сверять grep-ом по ключевым фразам.
6. **Скрипты как дыра.** Рецепты безопасны белым списком, а скрипты на языке проекта — нет. Защита — жёсткие правила §4.4 и то, что их пишет только драйвер. Скрипты в `.pumba/` коммиттер не коммитит (исключение `.pumba/`), их судьбу решает пользователь.
7. **Ложная уверенность в оценках.** Числа §2 — расчёт. Решение о v2/v3 — по замеру WP7.
