# Шаблоны pumba для Claude Code

Набор субагентов и скиллов, который ставится в `.claude/` любого проекта с доской pumba. После установки достаточно написать основному агенту «выполни задачу T-005» или «возьми эпик E-002»: он поведёт карточку по колонкам доски, запуская нужных субагентов, и будет переносить её так, чтобы pumba сразу показывал результат.

Ничего проектного в шаблонах нет: язык, команды сборки и тестов, стиль коммитов, ветки и порядок работы берутся из проекта и из `.pumba/` (`board.json`, правила колонок и «Правила проекта» в `.pumba/AGENTS.md`).

## Состав и куда ставится

| Файл в `templates/` | Куда ставится в проекте | Что это |
|---|---|---|
| `skills/pumba-task/SKILL.md` | `.claude/skills/pumba-task/SKILL.md` | драйвер: ведёт карточку по колонкам |
| `skills/pumba-new-card/SKILL.md` | `.claude/skills/pumba-new-card/SKILL.md` | создание карточки с правильным id и frontmatter |
| `agents/pumba-planner.md` | `.claude/agents/pumba-planner.md` | план задачи, порядок дочерних карточек эпика (только чтение) |
| `agents/pumba-tester.md` | `.claude/agents/pumba-tester.md` | тесты до реализации, приёмка, разбор падений (только файлы тестов) |
| `agents/pumba-worker.md` | `.claude/agents/pumba-worker.md` | реализация по плану (код проекта) |
| `agents/pumba-reviewer.md` | `.claude/agents/pumba-reviewer.md` | ревью с серьёзностью замечаний (только чтение) |
| `agents/pumba-committer.md` | `.claude/agents/pumba-committer.md` | один коммит по списку файлов и правилу «Стиль коммитов» |

Сам этот README в проект не ставится.

Пакеты для других ИИ-инструментов (Codex, Cursor, GitHub Copilot, OpenCode) лежат в `targets/<id>/` — готовыми файлами в раскладке проекта. Состав, отличия и ограничения — в `targets/README.md`, исследование форматов — в `TARGETS.md`.

## Что делает установщик

Команда установки (`pumba init [--tools <список>|--no-agents]` или `pumba install [--tools <список>] [--force]`; `install-claude` остался псевдонимом). Список — id через запятую или `all`: `claude`, `codex`, `cursor`, `copilot`, `opencode`. Без `--tools` в терминале спрашивает, для каких ИИ-инструментов ставить; выбор пишется в `board.json` (`tools`). Ниже описан пакет `claude`, файлы остальных — в `targets/README.md`. Если выбраны инструменты, которые читают чужие папки пакета (например Claude Code вместе с Cursor), установщик ставит всё и печатает предупреждение о возможных дублях скилла `pumba-task`:

1. Находит корень проекта — папку с `.pumba/` — и создаёт `.claude/agents/` и `.claude/skills/<имя>/`, если их нет.
2. Копирует файлы по таблице выше. Существующий файл **не перезаписывает**: пропускает его и пишет «пропущен, уже есть: <путь>». Перезапись — только с флагом `--force`.
3. Ничего не удаляет и не трогает другие файлы в `.claude/`.
4. В конце печатает, что поставлено, что пропущено, и подсказку: «Напишите агенту: выполни задачу T-001».

Шаблоны лучше вшить в бинарник (`include_str!`), чтобы установка не зависела от папки `templates/` рядом с программой.

## Как это работает

- **Драйвер** — основная сессия по скиллу `pumba-task`. Только он меняет файлы карточек. Цикл: прочитать карточку → найти её колонку → выполнить «Перед работой» (проверить, спросить, остановиться) → выполнить «Работу» (сам или субагентом из поля `agent`) → проверить «После работы» → перенести в колонку `next` или туда, куда велит «После работы» → повторить. Остановка — колонка без `next`, правило велит ждать человека, неудача после повышения модели, вопрос к человеку, блокировка зависимостями.
- **Исполнители** — субагенты. Делают работу колонки и заканчивают ответ строкой `ИТОГ: …`. Файлы `.pumba/` не меняют, карточки не двигают.
- **Порядок работы задаёт доска.** Скилл не знает, что после плана идут тесты, а после ревью — коммит: это написано в правилах колонок. Поменяли правила и `next` — поменялся процесс.
- **Правило колонки — три части**, драйвер читает их по порядку. В TUI это три поля формы колонки (`c` — новая, `r` — правка), в `board.json` — ключи `before`, `rule`, `after`:
  - «Перед работой» (`before`) — условия старта: что проверить, что спросить у пользователя, когда остановиться. Драйвер выполняет её до запуска любого исполнителя.
  - «Работа» (`rule`) — что делает исполнитель колонки (`agent`) и вспомогательные субагенты, пока карточка в колонке.
  - «После работы» (`after`) — как проверить результат, что делать при неудаче и куда идти при каждом исходе. Колонку для успеха задаёт `next`.
  - Пустая часть — на этом шаге делать нечего. На старых досках есть только `rule`: это «Работа», а «Перед работой» и «После работы» пусты.
- Вспомогательных субагентов, названных в правиле (планировщик, тестировщик, коммиттер), запускает драйвер, а `agent` — основной исполнитель колонки. Субагенты Claude Code умеют запускать своих (до 3 уровней), но пакет этим намеренно не пользуется: в Copilot вложенный запуск по умолчанию выключен, в Cursor субагент второго уровня уже никого не запускает, в Codex вложенность не описана. Один драйвер, который запускает всех, работает одинаково везде, и только он видит все `ИТОГ:`.
- **Ручное обновление доски** («Обновление доски: Вручную»): драйвер выполняет работу колонки, но перенос только предлагает и ждёт ответа. «Да» от пользователя — прямая просьба, драйвер переносит сам и продолжает.

## Колонки по умолчанию

Цепочка: `backlog` → (пользователь сказал «да») → `in-progress` → `review` → `done`. Ошибки после всех попыток уводят карточку в `on-dev`. `done` — последняя колонка: только она снимает блокировку `depends`.

Первая (`backlog`, «Бэклог») и последняя (`done`, «Готово») колонки закреплены по позиции: в pumba их нельзя двигать и удалять, новые колонки встают перед последней.

| id | Название | Цвет | `agent` | `next` | Перед работой | Работа | После работы |
|---|---|---|---|---|---|---|---|
| `backlog` | Бэклог | purple | — | — | предупредить, спросить «брать в работу?», без «да» остановиться | — | после «да» — в `in-progress` |
| `in-progress` | В работе | orange | `pumba-worker` | `review` | крупный план при «Сначала спрашивать» — только после подтверждения | план, тесты, реализация, проверки | проверки зелёные — дальше; неудача — разбор, повтор на модели выше, затем `on-dev` |
| `review` | На ревью | pink | `pumba-reviewer` | `done` | код не писать; «только проверь» — ревью без переноса | приёмка, ревью | одобрено — коммит и дальше; замечания — в `in-progress`, второй раз или хук — `on-dev` |
| `on-dev` | Ждёт разработчика | red | — | — | нет решения — напомнить и остановиться | — | решение есть — в `in-progress` |
| `done` | Готово | green | — | — | сообщить, что готово, предложить проверку, остановиться | проверка по просьбе, без переноса | — |

**Где коммит.** В «После работы» колонки «На ревью»: после одобрения ревью драйвер запускает `pumba-committer`, и только после коммита карточка уходит в «Готово». Почему так:

- в «Готово» попадает только закоммиченная и проверенная работа, поэтому зависимые карточки строятся на коде, который уже в истории;
- одна карточка — один чистый коммит: правки по ревью попадают в него же, а не отдельными коммитами «fix review»;
- ревьюер смотрит один дифф от точки старта, без смеси коммитов.

Нужна проверка человеком перед «Готово» — очистите `next` у `review` и уберите коммит из её «После работы»: тогда драйвер остановится после ревью, а коммит и перенос сделает человек.

## Правила проекта по умолчанию для этого процесса

| Правило | Значение | Почему |
|---|---|---|
| Стиль коммитов | `conventional` | понятен любому проекту и инструментам changelog; `pumba-committer` работает с любым вариантом. Нужна связь коммита с карточкой — `ticket`. |
| Модель ветвления | `per-task` | одна карточка — одна ветка `pumba/<id>-<slug>`: драйвер называет ветку однозначно, работу легко отложить и вернуть. Эпик — одна ветка на эпик. |
| Стратегия слияния | `squash` | карточка попадает в основную ветку одним коммитом, как и коммитит `pumba-committer`. |
| Тестирование | `required` | тестировщик пишет тесты до исполнителя: у исполнителя есть цель, у драйвера — объективное условие выхода. `tdd` строже, `optional` убирает тестировщика и приёмку. |
| Автономность | `ask` | процесс идёт сам, но крупные изменения (много файлов, удаления, зависимости) ждут подтверждения плана. Для долгих эпиков без человека — `autonomous`. |
| Обновление доски | `auto` | весь процесс держится на колонках: доска сразу показывает, где карточка, а после обрыва сессии драйвер продолжает с колонки. `manual` тоже работает, но каждый перенос ждёт ответа. |

## Модели субагентов

Во frontmatter у всех, кроме коммиттера, `model: inherit`: модель исполнителя задаёт драйвер параметром `model` инструмента Agent — из `model:` карточки, из плана или при повышении `haiku → sonnet → opus`. Зашитая модель мешала бы этому. У `pumba-committer` — `model: haiku`: работа механическая (индексировать список файлов, написать сообщение по правилу), сильная модель там только тратит токены.

## Что агент меняет в `.pumba/`

- Только драйвер, только строку `column:` существующим `id` из `board.json` и раздел `## Ход работы` в конце тела (только новые строки). Остальные ключи, порядок ключей и `---` не трогаются: pumba пишет frontmatter сам и выбрасывает незнакомые ключи.
- Новые карточки — только по просьбе пользователя, скиллом `pumba-new-card`.
- Файлы карточек не удаляются никогда: корзина в pumba мягкая (`deleted: true`), её ведёт TUI.
- `board.json` и `AGENTS.md` агенты не правят.
