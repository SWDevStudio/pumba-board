# Pumba Board

[English](README.en.md) · [Сайт](https://swdevstudio.github.io/pumba-board/) · [GitHub](https://github.com/SWDevStudio/pumba-board)

Канбан-доска в терминале для задач ИИ-агентов. Вы заводите карточки и настраиваете колонки, а агент (Claude Code, Codex, Cursor, Copilot или OpenCode) берёт карточку, проходит с ней по колонкам и двигает её сам. Всё лежит в папке `.pumba/` рядом с кодом.

Это руководство идёт по шагам: установка, первый запуск, карточки, правила, работа агента и пример с закрытой задачей. Если нужна только общая картина, откройте [сайт проекта](https://swdevstudio.github.io/pumba-board/).

## 1. Что это и зачем

Pumba Board это программа на Rust с интерфейсом в терминале (TUI). Бинарник называется `pumba`.

Зачем она нужна. Агенту нужно знать три вещи: что делать, в каком порядке и когда остановиться. Обычно это лежит в голове у человека или в длинном промпте. Pumba переносит это в файлы проекта:

- **карточки** описывают, что сделать (один файл на карточку);
- **колонки** задают этапы, а правило каждой колонки говорит агенту, что проверить до работы, что сделать и что проверить после;
- **правила проекта** фиксируют стиль коммитов, ветки, слияние, тесты и автономность.

Порядок работы задаёт доска, а не программа и не скилл агента. Поменяли правила колонок, и процесс стал другим.

Что важно знать сразу:

- интерфейс программы и колонки по умолчанию на русском языке;
- данные хранятся в обычных файлах: `.pumba/board.json`, `.pumba/tasks/<ID>.md`, `.pumba/AGENTS.md`;
- программа сама подхватывает правки этих файлов, сделанные снаружи (агентом, редактором, `git checkout`);
- агент двигает карточку, меняя одну строку `column:` в её файле.

## 2. Установка

### Готовый бинарник

На странице [Releases](https://github.com/SWDevStudio/pumba-board/releases) лежат сборки для Windows (`x86_64-pc-windows-msvc`, `.zip`) и Linux (`x86_64-unknown-linux-musl`, `.tar.gz`, статическая, без зависимостей). Распакуйте архив и положите `pumba` в папку из `PATH`. Рядом с каждым архивом есть файл `.sha256` с контрольной суммой.

### Из исходников

Нужен Rust. В `Cargo.toml` указана редакция 2024, поэтому подойдёт Rust 1.85 или новее.

```bash
git clone git@github.com:SWDevStudio/pumba-board.git
cd pumba-board
cargo install --path .
```

Крейт называется `pumba-board`, бинарник `pumba`. Проверка:

```bash
pumba --version
pumba --help
```

`pumba --help` печатает полную справку по командам и опциям.

## 3. Первый запуск и `init`

Есть два пути: открыть программу или создать доску командой.

### Через программу

Перейдите в папку проекта и запустите `pumba`:

```bash
cd ~/projects/shop
pumba
```

Программа ищет `.pumba/board.json` в этой папке и выше. Если не нашла, она спросит: «Папка .pumba/ не найдена. Создать её в …?». Ответьте `y` или Enter. Затем появится список инструментов, для которых поставить агентов и скиллы:

- уже найденные в проекте инструменты отмечены заранее; если ничего не найдено, отмечен Claude Code;
- `↑`/`↓` (или `k`/`j`) перемещают курсор, пробел ставит и снимает отметку, `a` отмечает или снимает всех;
- Enter создаёт доску и ставит набор, Esc создаёт только `.pumba/` без агентов (поставить их можно позже клавишей `I`).

### Через командную строку

```bash
pumba init                       # создать .pumba/ и спросить про инструменты
pumba init --tools claude,cursor # без вопроса
pumba init --no-agents           # только .pumba/, без агентов и скиллов
pumba init ~/projects/shop       # другой каталог
```

Если `.pumba/` уже есть, `init` напишет «Уже инициализировано» и только доустановит набор. Существующие файлы он не перезаписывает.

Без `--tools` в терминале `init` задаёт вопрос со списком: отвечайте номерами через запятую (`1,3`), пустая строка принимает отмеченное, `0` значит «никого». Если терминала нет (скрипт, CI), берётся список из `tools` в `board.json`, иначе найденные в проекте инструменты, иначе Claude Code. Выбор записывается в `board.json`.

### Все команды

| Команда | Что делает |
|---|---|
| `pumba [ПУТЬ]` | открывает доску; если `.pumba/` нет, предлагает создать |
| `pumba init [--tools СПИСОК \| --no-agents] [ПУТЬ]` | создаёт `.pumba/` и ставит агентов и скиллы |
| `pumba install [--tools СПИСОК] [--force] [ПУТЬ]` | ставит или обновляет только агентов и скиллы |
| `pumba install-claude [--force] [ПУТЬ]` | то же, что `install --tools claude` |
| `pumba --help`, `pumba --version` | справка и версия |
| `pumba brief`, `move`, `note`, `rules`, `unblocks`, `column`, `rules-hash` | команды для агентов, не открывают доску (см. «Команды CLI для агентов» в разделе 9) |

`ПУТЬ` это каталог проекта, по умолчанию текущий. Доска ищется вверх от него. Допустимые id инструментов: `claude`, `codex`, `cursor`, `copilot`, `opencode` или `all`.

### Что создаётся

После `init` в проекте появляются:

```
.pumba/
  board.json    колонки, правила колонок, правила проекта, спринт
  tasks/        карточки (пока пусто)
  AGENTS.md     инструкции для агентов, программа пересобирает его сама
```

и файлы агентов в папках выбранных инструментов (подробности в [разделе 8](#8-набор-для-агента-pumba-install)).

## 4. Интерфейс и навигация

Экран делится на четыре части:

1. **Шапка**: метка PUMBA, имя проекта, номер спринта, пометки `[только спринт]` и `[скрытые видны]`, счётчик корзины.
2. **Колонки с карточками.** Заголовок колонки: `● Название  число карточек`, цвет колонки задан в её настройках. Выбранная карточка обведена оранжевой рамкой. Если колонки не помещаются по ширине, в шапке справа появляется `кол. 2-4/5`.
3. **Панель деталей**: слева название, колонка, модель, уровень, спринт, эпик, зависимости и описание выбранной карточки, справа правило выбранной колонки по трём частям.
4. **Строка подсказок** с основными клавишами. Сообщения об ошибках и успехе тоже появляются здесь.

### Как выглядит карточка

Карточка на доске занимает четыре строки в рамке:

1. маркер (`▪` задача, `◆` эпик), номер и, если заданы, `модель*уровень`, например `▪ T-005  opus*high`;
2. две строки названия;
3. нижняя строка с метками.

Метки в нижней строке:

| Метка | Значение |
|---|---|
| `S1` | карточка в спринте 1 |
| `↳ E-001` | родитель: эпик E-001 |
| `⊘ T-003` | заблокирована: T-003 ещё не в последней колонке |
| `✓ зав.` | у карточки есть зависимости, и все выполнены |
| `→ T-007,T-008` | эти карточки ждут её |
| `скрыта` | карточка скрыта (видна только при `v`) |
| `▰▰▱▱ 2/4` | у эпика: сколько дочерних задач в последней колонке |
| `?колонка` | в файле указана колонка, которой нет; карточка показана в первой |


### Горячие клавиши

Справка в программе открывается клавишей `?`. Русская раскладка (ЙЦУКЕН) работает: клавиши распознаются по расположению.

**Карточки**

| Клавиша | Действие |
|---|---|
| `n` | новая задача |
| `N` | новый эпик |
| `Enter` / `e` | правка карточки |
| `d` | в корзину |
| `x` | скрыть / показать карточку |
| `p` | в текущий спринт / из спринта |
| `H` / `L` (или `Shift+←` / `Shift+→`) | в предыдущую / следующую колонку |
| `J` / `K` | порядок в колонке вниз / вверх |

**Колонки**

| Клавиша | Действие |
|---|---|
| `c` | новая колонка (встаёт перед последней) |
| `r` | правка колонки и её правила |
| `X` | удалить колонку |
| `Ctrl+←` / `Ctrl+→` (или `Alt`, или `<` `>`) | сдвинуть колонку влево / вправо |

**Вид**

| Клавиша | Действие |
|---|---|
| `h` / `l` (или `←` / `→`) | выбор колонки |
| `j` / `k` (или `↓` / `↑`) | выбор карточки |
| `v` | показать / скрыть скрытые карточки |
| `s` | фильтр: только текущий спринт |
| `?` | справка |
| `q` или `Ctrl+C` | выход |

**Проект**

| Клавиша | Действие |
|---|---|
| `]` | начать следующий спринт |
| `P` | правила проекта для агентов |
| `M` | модели и уровни размышления |
| `B` | корзина (восстановить карточку) |
| `I` | агенты и скиллы (инструменты) |
| `@` | вставить ссылку на файл (в полях описания) |

### Формы и подсказки

Правка карточки, колонки, правил и моделей открывается формой.

- `Tab` и `Shift+Tab` переключают поля, `↑`/`↓` тоже (в многострочном поле `↑`/`↓` сначала двигают курсор). В двухколоночной форме `Ctrl+←`/`Ctrl+→` прыгают между колонками полей.
- `Ctrl+S` сохраняет, `Esc` или `Ctrl+C` отменяет.
- В полях-переключателях меняйте значение `←`/`→` или пробелом. Если вариантов восемь и больше, можно просто набирать буквы: список фильтруется, Enter или Tab выбирает.
- Ошибка проверки (например, пустое название) показывается в строке состояния, форма остаётся открытой.

Подсказки, чтобы не набирать значения вручную:

- **`@` в описании.** В многострочных полях (описание карточки, части правила колонки, свои правила) символ `@` открывает список файлов и папок проекта с поиском по набранному. `↑`/`↓` двигают выбор, Enter или Tab вставляют `@путь/к/файлу`, Esc закрывает список. Список не показывает файлы и папки с точкой в начале имени и каталоги вроде `node_modules`, `target`, `dist`, `build`, `.git`. Агент прочитает эти файлы перед работой.
- **Поля «Зависит от» и «Блокирует».** Набираете часть id, названия, текста описания или названия колонки, программа показывает подходящие карточки (эпики отмечены), Enter или Tab вставляет id в список через запятую.
- **Поле «Исполнитель» у колонки.** Программа просматривает папки агентов проекта (`.claude/agents`, `.codex/agents`, `.cursor/agents`, `.github/agents`, `.opencode/agents`) и предлагает имена найденных субагентов. Агенты `pumba-*` стоят первыми. Список строится заново при каждом открытии формы.

## 5. Эпики, задачи, зависимости, спринты, скрытие, корзина

### Создать эпик и задачу

1. Выберите колонку, куда положить карточку. **Новая карточка попадает в ту колонку, которая выбрана сейчас.** Обычно это «Бэклог».
2. `N` создаёт эпик, `n` создаёт задачу.
3. Заполните форму и нажмите `Ctrl+S`.

Поля формы:

| Поле | Что это |
|---|---|
| Название | одна строка, обязательно |
| Описание для агента | бриф в Markdown: что сделать, где, критерии приёмки; здесь работает подсказка `@` |
| Модель | подсказка агенту: `default` или модель из списка (по умолчанию `opus`, `sonnet`, `haiku`) |
| Уровень | уровень размышления: `default` или `low`, `medium`, `high`, `xhigh`, `max` |
| Спринт | нет, текущий или следующий |
| Эпик | родитель (только у задачи) |
| Зависит от | id карточек через запятую |
| Блокирует | id карточек, которые ждут эту |

Номера выдаются автоматически: `E-001`, `E-002` для эпиков и `T-001`, `T-002` для задач. Номер совпадает с именем файла. Если перед `n` выбран эпик, он сразу подставляется в поле «Эпик». Модель и уровень в новой форме берутся из значений по умолчанию (см. `M` ниже).

Карточку можно открыть и поправить: `Enter` или `e`.

### Модель и уровень размышления

Это подсказки агенту, а не жёсткие настройки. Значение `default` значит «без предпочтений». Агент передаёт модель и уровень исполнителю так, как умеет его инструмент. Клавиша `M` открывает форму, где можно изменить списки моделей и уровней (по одному значению в строке) и выбрать значения по умолчанию для новых карточек.

### Зависимости и «Блокирует»

В поле «Зависит от» перечислите карточки, которые должны быть сделаны раньше. Пока хотя бы одна из них не лежит **в последней колонке**, карточка заблокирована:

- на доске у неё метка `⊘ T-003`, в панели деталей красная надпись «ЗАБЛОКИРОВАНА»;
- если перенести заблокированную карточку (не в первую колонку), программа предупредит в строке состояния: «Заблокирована: T-003»;
- агент откажется брать такую карточку и назовёт блокирующие.

Поле «Блокирует» это то же самое с другой стороны: перечислите карточки, которые ждут эту. Программа допишет вашу карточку в их `depends:`. В самой карточке «Блокирует» не хранится, оно вычисляется.

Программа проверяет ссылки. Карточка не может зависеть от самой себя, зависеть от несуществующей или лежащей в корзине, и не может одновременно зависеть от другой и блокировать её. Цикл (A зависит от B, B зависит от A) программа не примет: «Цикл зависимостей: T-001 → T-002 → T-001».

Карточка из корзины зависимостью не считается и никого не блокирует.

### Спринты

В шапке показан текущий спринт. Спринт это просто номер на карточке.

- `p` кладёт выбранную карточку в текущий спринт или убирает из него.
- `s` переключает фильтр «только текущий спринт».
- `]` начинает следующий спринт. Программа спросит подтверждение и перенесёт в новый спринт все незавершённые карточки старого (те, что не в последней колонке).

### Скрытие

`x` прячет выбранную карточку (она остаётся в файлах). `v` показывает или прячет скрытые карточки. Скрытая карточка выглядит курсивом с пометкой `скрыта`.

### Корзина вместо удаления

`d` спрашивает подтверждение и отправляет карточку в корзину. Файл остаётся в `.pumba/tasks/`, в нём появляется `deleted: true`. Номер из корзины никогда не выдаётся повторно.

`B` открывает корзину: `↑`/`↓` выбирают карточку, `Enter` или `r` восстанавливают, `Esc`, `q` или `B` закрывают. У эпика в корзине дочерние задачи остаются на месте. Агенты полностью игнорируют карточки из корзины.

### Перенос и порядок

`H` и `L` переносят карточку в соседнюю колонку, `J` и `K` меняют порядок внутри колонки. Вручную можно переносить карточку куда угодно: блокировка зависимостей только предупреждает человека, а агента останавливает.

## 6. Настройка колонок

`c` создаёт колонку, `r` открывает правку выбранной. Новая колонка встаёт перед последней.

### Поля формы колонки

| Поле | Что это |
|---|---|
| Название | как колонка называется на доске |
| Перед работой (проверки, стоп) | условия старта |
| Работа (что делает исполнитель) | что происходит, пока карточка в колонке |
| После работы (проверка, куда) | как проверить результат и куда идти |
| Исполнитель (пусто — нет) | субагент колонки, с подсказкой имён |
| После успеха | следующая колонка (`next`) или «нет» |
| Цвет | фиолетовый, оранжевый, зелёный, красный, розовый, песочный |

### Три части правила

Агент читает правило колонки по частям и строго по порядку.

1. **Перед работой** (`before`): что проверить, что спросить у пользователя, когда остановиться. Агент выполняет это раньше всего, до запуска любого исполнителя. Например, колонка «Бэклог» велит предупредить, что задача не запланирована, и спросить «брать в работу?». Без «да» агент останавливается.
2. **Работа** (`rule`): что делает исполнитель колонки, пока карточка в ней. Здесь можно назвать и вспомогательных субагентов: «сначала `pumba-planner`, затем `pumba-tester`».
3. **После работы** (`after`): как проверить результат, что делать при неудаче и куда перенести карточку при каждом исходе.

Пустая часть означает, что на этом шаге делать нечего. На старых досках, где есть только `rule`, он считается «Работой».

Правило пишется обычным текстом: агент его читает и выполняет. В частях можно ссылаться на субагентов по имени, на другие колонки по id и на правила проекта.

### Субагент и следующая колонка

**Исполнитель** (`agent`) это субагент, который делает «Работу» колонки. Пусто значит, что работу делает сам агент-драйвер или человек. **После успеха** (`next`) это колонка, в которую карточка уходит после успешной работы. Пусто значит «остановиться и отчитаться, карточку перенесёт человек». Колонка не может вести сама в себя.

### Закреплённые колонки

Первая и последняя колонки закреплены по позиции:

- их нельзя двигать (`Ctrl+←`/`→`) и удалять (`X`);
- новые колонки встают перед последней;
- **последняя колонка завершающая**: только она снимает блокировку `depends`.

Удаление другой колонки переносит её карточки в первую из оставшихся, а ссылки `next` на неё очищаются.

### Колонки по умолчанию

| Колонка | Цвет | Исполнитель | Дальше | Что происходит |
|---|---|---|---|---|
| Бэклог | фиолетовый | нет | нет | агент предупреждает и спрашивает «брать в работу?»; после «да» переносит в «В работе» |
| В работе | оранжевый | `pumba-worker` | На ревью | планировщик составляет план, тестировщик пишет тесты (если тесты обязательны), исполнитель реализует, агент запускает проверки; при неудаче повтор на модели выше, потом «Ждёт разработчика» |
| На ревью | розовый | `pumba-reviewer` | Готово | приёмка и ревью; после одобрения `pumba-committer` делает один коммит; замечания возвращают карточку в «В работе», второй возврат за прогон уводит в «Ждёт разработчика» |
| Ждёт разработчика | красный | нет | нет | агент остановился и ждёт решения человека; решение есть, и карточка возвращается в «В работе» |
| Готово | зелёный | нет | нет | карточка выполнена; по просьбе агент проверит результат без правок |

Весь процесс лежит в `board.json` и легко меняется: уберите коммит из «После работы» у «На ревью» и очистите её «После успеха», и после ревью агент остановится, а коммит и перенос сделаете вы.

## 7. Правила проекта и `.pumba/AGENTS.md`

Клавиша `P` открывает «Правила проекта»: шесть переключателей и поле «Свои правила (Markdown)». Менять значение можно `←`/`→` или пробелом. `Ctrl+S` сохраняет.

| Правило | Варианты (по умолчанию выделен) |
|---|---|
| Стиль коммитов | **Conventional Commits**, Gitmoji, префикс с ID задачи, свободный формат |
| Модель ветвления | GitHub Flow, Git Flow, Trunk-based, **ветка на задачу** (`pumba/<id>-<slug>`) |
| Стратегия слияния | **squash**, merge-коммит, rebase |
| Тестирование | **тесты обязательны**, TDD, тесты по желанию |
| Автономность | **сначала спрашивать** перед крупными изменениями, автономно |
| Обновление доски | **агент двигает задачи**, вручную |

Два правила влияют на поведение агента сильнее остальных:

- **Автономность: «Сначала спрашивать»**. Перед крупным изменением (много файлов, удаления, смена зависимостей) агент показывает план и ждёт подтверждения. Для долгих эпиков без человека выберите «Автономно».
- **Обновление доски: «Вручную»**. Агент не трогает `.pumba/` по своей инициативе: он предлагает перенос и ждёт ответа. Ответ «да» считается прямой просьбой, и агент переносит карточку сам.

Поле «Свои правила» принимает любой Markdown: договорённости по именованию, запреты, ссылки на документацию. Всё это попадёт в `AGENTS.md` в раздел «Свои правила».

### Как собирается `AGENTS.md`

Программа генерирует `.pumba/AGENTS.md` при каждом изменении доски. Руками его править не нужно, правки перезапишутся. В файле:

1. **Протокол** из 13 пунктов: как читать карточку, как применять правило колонки, жёсткое правило про зависимости (агент обязан отказаться от заблокированной карточки), как понимать ссылки `@путь`, что карточки из корзины игнорируются, что двигает карточки только основной агент, и что краткие решения записываются в раздел «Ход работы».
2. **Правила колонок**: для каждой колонки «Перед работой», «Работа» с исполнителем и «После работы» с колонкой после успеха.
3. **Правила проекта** и «Свои правила».
4. **Индекс задач**: таблица `id | тип | колонка | спринт | depends | blocks | название` (карточки из корзины в неё не попадают).

Индекс может отставать от файлов карточек, поэтому колонку, `parent` и `depends` агент всегда берёт из самих карточек. Если правила колонок в `AGENTS.md` расходятся с `board.json`, верить нужно `board.json`.

## 8. Набор для агента: `pumba install`

В набор входят **пять субагентов** и **два скилла**.

| Файл | Роль |
|---|---|
| `pumba-task` (скилл) | драйвер: ведёт карточку по колонкам |
| `pumba-new-card` (скилл) | создаёт карточку с правильным номером и frontmatter |
| `pumba-planner` | план задачи или порядок дочерних карточек эпика; только чтение |
| `pumba-tester` | тесты до реализации, приёмка, разбор упавших проверок |
| `pumba-worker` | реализация по плану |
| `pumba-reviewer` | ревью с серьёзностью замечаний (блокирует, стоит поправить, мелочь); только чтение |
| `pumba-committer` | один коммит по правилу «Стиль коммитов»; не пушит и не меняет историю |

```bash
pumba install --tools claude,codex,cursor,copilot,opencode
pumba install --tools all
pumba install --tools claude --force   # перезаписать существующие файлы
```

Установка:

- ничего не удаляет и не трогает чужие файлы;
- существующие файлы пропускает («пропущен»); перезапись только с `--force`, но файл, совпадающий по содержимому, всё равно считается пропущенным;
- записывает выбор инструментов в `board.json` (поле `tools`);
- в конце печатает, сколько файлов установлено и пропущено.

Если выбраны инструменты, которые читают папки друг друга, она печатает предупреждение о возможных копиях скилла `pumba-task`, но всё равно ставит файлы. Такие сочетания: Claude Code с Cursor, Copilot или OpenCode; Codex с Cursor, Copilot или OpenCode. Если инструмент выберет не свою копию, удалите лишнюю.

Внутри программы то же делает клавиша `I`: список инструментов с отметками, `Enter` ставит.

### Что создаётся для каждого инструмента

**Claude Code** (`claude`, 7 файлов)

- `.claude/agents/pumba-planner.md`, `pumba-tester.md`, `pumba-worker.md`, `pumba-reviewer.md`, `pumba-committer.md`
- `.claude/skills/pumba-task/SKILL.md`, `.claude/skills/pumba-new-card/SKILL.md`
- вызов: «выполни задачу T-001» или `/pumba-task T-001`

**OpenAI Codex** (`codex`, 7 файлов)

- `.codex/agents/pumba-*.toml` (пять агентов; внутри `name = "pumba_worker"` и так далее, с подчёркиванием)
- `.agents/skills/pumba-task/SKILL.md`, `.agents/skills/pumba-new-card/SKILL.md`
- вызов: `$pumba-task` или просьба «выполни задачу T-001»

**Cursor** (`cursor`, 8 файлов)

- `.cursor/agents/pumba-*.md` (пять агентов; planner и reviewer с `readonly: true`)
- `.cursor/skills/pumba-task/SKILL.md`, `.cursor/skills/pumba-new-card/SKILL.md`
- `.cursor/rules/pumba.mdc`: короткий указатель на `.pumba/AGENTS.md` и скиллы
- вызов: `/pumba-task T-001`

**GitHub Copilot** (`copilot`, 8 файлов; VS Code и облачный агент)

- `.github/agents/pumba-*.agent.md` (пять агентов, скрыты из списка и запускаются драйвером)
- `.github/skills/pumba-task/SKILL.md`, `.github/skills/pumba-new-card/SKILL.md`
- `.github/instructions/pumba.instructions.md`: указатель с `applyTo: ".pumba/**"`
- вызов: `/pumba-task T-001`

**OpenCode** (`opencode`, 9 файлов)

- `.opencode/agents/pumba-*.md` (пять агентов, режим `subagent`, права заданы через `permission`)
- `.opencode/skills/pumba-task/SKILL.md`, `.opencode/skills/pumba-new-card/SKILL.md`
- `.opencode/commands/pumba-task.md`, `.opencode/commands/pumba-new-card.md`: команды `/pumba-task <id>` и `/pumba-new-card <описание>`

Пакеты для разных инструментов ведут один и тот же цикл. Различия в том, чем запускается субагент, как выбирается модель и какие права задаёт сам инструмент. Подробности, ссылки на документацию и ограничения каждого инструмента лежат в [`templates/targets/README.md`](templates/targets/README.md) и [`templates/TARGETS.md`](templates/TARGETS.md).

Имена моделей на доске (`haiku`, `sonnet`, `opus`) это имена моделей Claude. В остальных инструментах они читаются как уровни сложности: как именно, написано в разделе 3 скилла `pumba-task` для каждого пакета.

## 9. Как дать задачу агенту

Откройте агента в папке проекта и напишите по-русски:

- «выполни задачу T-001»
- «возьми карточку T-012», «сделай T-3»
- «возьми эпик E-002»
- «продолжи T-005»
- «создай карточку: …», «заведи задачу», «разбей эпик E-002 на задачи» (это уже `pumba-new-card`)

Можно вызвать скилл явно: `/pumba-task T-001` (в Codex `$pumba-task`).

### Что делает агент по скиллу `pumba-task`

**Приём карточки**

1. Нормализует id: `t-5`, `T5`, `т-005` становятся `T-005`. Файла нет: агент говорит об этом и останавливается, карточку не создаёт.
2. Карточка в корзине (`deleted: true`): отказывается.
3. **Проверяет зависимости.** Для каждого id из `depends:` читает файл. Хоть одна зависимость не в последней колонке: агент отказывается, перечисляет их («T-003 - «В работе» (`in-progress`)») и предлагает заняться ими. Блокировку он не обходит даже по просьбе.
4. Читает «Правила проекта», «Свои правила» и, если есть, `CLAUDE.md` и `AGENTS.md` в корне проекта.
5. Проверяет, что ссылки `@путь` из описания существуют.

**Цикл по колонкам**

1. Перечитывает карточку (вы могли перенести её в программе) и находит её колонку в `board.json`.
2. **Перед работой**: проверяет условия, предупреждает или спрашивает. Правило велит остановиться, и агент останавливается, не двигая карточку.
3. **Работа**: запускает исполнителя колонки (поле `agent`) и вспомогательных субагентов в порядке, который назвала «Работа». Если исполнителя нет, делает сам. Нужного субагента нет в проекте: остановка с названием недостающего.
4. **После работы**: проверяет результат не на слово, а сам: запускает проверки, читает `ИТОГ:` исполнителя, смотрит последний коммит. При неудаче повторяет на модели выше по лестнице `haiku → sonnet → opus`, по одной попытке на ступень. Не помогло на `opus` или нужен человек: карточка уходит в «Ждёт разработчика».
5. Переносит карточку в нужную колонку (командой `pumba move`, а без команды правкой строки `column:`) и возвращается к шагу 1.

**Остановки.** Цикл прерывается, когда:

- карточка в корзине или заблокирована;
- у колонки пустая «После успеха», и «После работы» не говорит, куда дальше;
- «Перед работой» или «После работы» велит ждать решения человека;
- исполнитель не справился на `opus`;
- при правиле «Сначала спрашивать» план помечен «Крупное изменение: да», и вы его ещё не подтвердили;
- включено ручное обновление доски: каждый перенос ждёт вашего ответа;
- возник вопрос, на который нельзя ответить из карточки, плана и правил;
- карточка в третий раз за прогон попала в одну и ту же колонку.

**Как запускаются исполнители.** Субагентов запускает только основная сессия (драйвер), исполнители никого не вызывают. В задание субагенту драйвер кладёт корень проекта, карточку, правило колонки, план и точку старта. Приёмку, разбор падения и ревью делает новый экземпляр субагента, а не тот, кто писал код. После тестировщика драйвер запоминает хеши файлов тестов и проверяет, что исполнитель их не менял.

**Git.** Перед первым исполнителем, который меняет файлы, драйвер смотрит `git status --short` и не трогает чужие незакоммиченные изменения. Ветку выбирает по правилу «Модель ветвления» (например, `pumba/T-005-login-form`). Коммитит только `pumba-committer` и только там, где велит правило колонки. Push, слияние, pull request, `--force`, `--amend`, `rebase` и `reset` агент делает только по прямой просьбе.

**Эпик** проходит колонки так же. В колонке с исполнителем драйвер вместо исполнителя ведёт дочерние карточки: порядок и волны подсказывает `pumba-planner` в режиме `epic`, карточки из бэклога драйвер просит взять в работу один раз за весь эпик. Эпик выходит из колонки, когда все дочерние в последней.

**Что агент оставляет на доске**

- После остановки отчёт (до 20 строк): где карточка и почему остановился; что сделано по колонкам; изменённые файлы и результат проверок; замечания ревью; коммит и ветка; что нужно от вас; какие карточки разблокированы.
- В теле карточки, в разделе `## Ход работы`, он дописывает короткие строки вида `- 2026-10-31 14:05 - «В работе» → «На ревью»: проверки зелёные, исполнитель pumba-worker (sonnet).` Решил что-то сам или сделал не так, как в карточке: пишет 1-3 строки, что и почему. При ручном обновлении доски `.pumba/` не правится, а запись агент говорит вам.

**Чего агент не делает.** Не удаляет файлы карточек. Не создаёт карточки и номера сам (только скиллом `pumba-new-card` по вашей просьбе). Не меняет `title`, `type`, `parent`, `depends`, `order`, `sprint`, `model`, `effort`, `hidden` без просьбы. Не правит `board.json` и `AGENTS.md`. Не переносит карточку в колонку, которой нет в «После успеха» или в частях правила.

### Скилл `pumba-new-card`

Создаёт карточку файлом `.pumba/tasks/<ID>.md` по вашей просьбе. Перед созданием проверяет дубли названий (включая корзину), что родитель существует и это эпик, что зависимости существуют и нет циклов, что колонка есть в `board.json`. Номер берёт как максимум среди всех файлов, включая корзину, плюс один. Если зависимость ещё не выполнена, скажет, что новая карточка заблокирована. Работу над созданной карточкой не начинает, пока вы не попросите.

### Команды CLI для агентов

Кроме интерфейса, программа умеет несколько команд для агентов. Они не задают вопросов и не открывают доску, а печатают короткий текст (с `--json` - один JSON-объект). Драйвер по скиллу `pumba-task` вызывает одну команду вместо нескольких чтений и правок файлов: меньше вызовов, меньше текста в контексте. `--root ПУТЬ` задаёт, откуда искать `.pumba/` вверх; без него поиск идёт от текущей папки.

| Команда | Что делает |
|---|---|
| `pumba brief ID [--known ЧАСТИ] [--body head\|full\|none]` | всё для шага драйвера: статус карточки, поля, колонка с тремя частями правила, зависимости, метки правил, хеши, последние переносы, начало тела |
| `pumba move ID КОЛОНКА\|next [--expect-from КОЛОНКА] [--note "ТЕКСТ"] [--user-approved]` | переносит карточку в конец колонки и дописывает заметку в `## Ход работы` |
| `pumba note ID "ТЕКСТ" [--user-approved]` | дописывает заметку в `## Ход работы` |
| `pumba rules [--part ID]` | «Правила проекта» и «Свои правила» одним блоком: драйвер вставляет его в задание субагенту |
| `pumba unblocks ID` | какие карточки ждут эту и что с ними будет |
| `pumba column КОЛОНКА` | одна колонка: три части правила, исполнитель, следующая колонка |
| `pumba rules-hash [--parts]` | отпечаток правил (12 символов) |

Команд для создания карточек, списка карточек и запуска скриптов нет: новые карточки по-прежнему создаёт скилл `pumba-new-card`.

Первая строка `brief` - статус: `OK`, `BLOCKED`, `DELETED` (корзина), `NO-PIPELINE` (у колонок нет ни исполнителя, ни следующей колонки), `UNKNOWN-COLUMN` (колонки карточки нет на доске). Так выглядит ответ для карточки, которая ждёт незавершённую зависимость (демо-доска с двумя задачами, T-002 зависит от T-001; код выхода 5):

```
$ pumba brief T-002
BLOCKED T-001 «Бэклог» (backlog)
T-002 task «slugify убирает знаки препинания и схлопывает дефисы» sprint=1 model=sonnet effort=medium api=1
col=backlog «Бэклог» (1/5) agent=- next=- last=done
parent=E-001 «Надёжные текстовые утилиты» backlog | depends: T-001 backlog ✗ | dependents: -
board=auto commits=conventional branching=per-task merge=squash tests=required autonomy=ask
hash rules=37cc79b9b0cb col:backlog=b60f4f3fad09
log: -; visits=0
pumba: T-002 BLOCKED (5)
```

Агент по такому ответу отказывается по жёсткому правилу и называет блокирующие карточки. Для карточки без блокировок первые строки те же, а после них идут непустые части правила колонки («Перед работой», «Работа», «После работы») дословно и тело карточки (здесь они опущены):

```
$ pumba move T-001 in-progress --note "пользователь подтвердил"
T-001: backlog → in-progress
$ pumba brief T-001 --body none
OK T-001 task «word_count считает пустые элементы при нескольких пробелах» sprint=1 model=sonnet effort=low api=1
col=in-progress «В работе» (2/5) agent=pumba-worker next=review «На ревью» last=done
parent=E-001 «Надёжные текстовые утилиты» backlog | depends: - | dependents: T-002
board=auto commits=conventional branching=per-task merge=squash tests=required autonomy=ask
hash rules=37cc79b9b0cb col:in-progress=1cc328b29636
log: 2026-10-31 18:00 UTC «Бэклог»→«В работе»; visits=1
## Работа
(текст правила колонки)
```

На следующих кругах цикла агент передаёт хеши из строки `hash`, и уже виденные части не повторяются:

```
$ pumba brief T-001 --body none --known rules=37cc79b9b0cb,col:in-progress=1cc328b29636
OK T-001 task «word_count считает пустые элементы при нескольких пробелах» sprint=1 model=sonnet effort=low api=1
col=in-progress «В работе» (2/5) agent=pumba-worker next=review «На ревью» last=done
parent=E-001 «Надёжные текстовые утилиты» backlog | depends: - | dependents: T-002
board=auto
hash rules=37cc79b9b0cb col:in-progress=1cc328b29636
known: col:in-progress, rules
log: 2026-10-31 18:00 UTC «Бэклог»→«В работе»; visits=1
```

Остальные команды отвечают одной строкой:

```
$ pumba note T-001 "план готов, тесты написаны"
T-001: заметка добавлена
$ pumba unblocks T-001
T-002 «slugify убирает знаки препинания и схлопывает дефисы» — разблокируется, когда T-001 дойдёт до «Готово»
$ pumba move T-001 next --expect-from in-progress --note "проверки зелёные"
T-001: in-progress → review
$ pumba rules-hash
37cc79b9b0cb
```

`--expect-from` защищает от параллельной правки: если карточка уже не в названной колонке, `move` ничего не пишет и выходит с кодом 6. Перенос вперёд при незавершённых зависимостях команда тоже отклоняет (код 5).

При ручном обновлении доски команды записи без `--user-approved` ничего не пишут, выходят с кодом 7 и печатают готовую фразу для пользователя:

```
$ pumba move T-001 in-progress
Обновление доски: «Вручную». Предложи пользователю:
«Перенести T-001 «word_count считает пустые элементы при нескольких пробелах» из «Бэклог» в «В работе». Сделать? (да/нет)»
После его явного «да» повтори команду с --user-approved.
pumba: доска в ручном режиме: без согласия пользователя не пишу (нужен --user-approved) (7)
```

Агент ставит `--user-approved` только после явного «да» пользователя.

**Коды выхода**

| Код | Смысл |
|---|---|
| 0 | успех (в том числе «уже так») |
| 1 | ошибка ввода-вывода |
| 2 | неверные аргументы |
| 3 | нет карточки, колонки или следующей колонки |
| 4 | карточка в корзине |
| 5 | заблокирована зависимостями |
| 6 | конфликт записи или не совпал `--expect-from` |
| 7 | запрещено ручным режимом доски (нужен `--user-approved`) |
| 9 | доски нет или `board.json` не читается |

**Скрипты агента.** Если агент три раза подряд повторяет одну и ту же последовательность команд (например, проверки перед коммитом), он сохраняет её в `.pumba/scripts/<имя>.sh` (на Windows `.ps1`) с шапкой из комментариев: `# pumba-script: <имя>`, `# purpose: …`, `# usage: …`, `# pumba-rules-hash: <вывод pumba rules-hash>`. Перед запуском агент сравнивает хеш из шапки с выводом `pumba rules-hash`. Хеши не совпали: правила доски изменились, агент перечитывает нужные части (`pumba rules`, `pumba column ID`) и переписывает или удаляет скрипт, а не запускает старый. Скрипт только читает и запускает проверки проекта, `.pumba/` в обход команд не правит и не содержит ничего необратимого (`push`, `reset`, удаление файлов). Программа эту папку не читает и сама скрипты не создаёт и не запускает.

**Если `pumba` нет в PATH.** Агент один раз за сессию проверяет `pumba --help`. Команды нет или в справке нет `pumba brief` (старая версия): агент работает по ручному протоколу, описанному выше, - он остался полным. Команды ускоряют работу, но не заменяют протокол.

## 10. Рабочий пример: от пустой папки до закрытой задачи

Допустим, делаем маленький магазин и работаем с Claude Code.

**1. Папка и доска**

```bash
mkdir shop && cd shop
git init
pumba init --tools claude
```

Вывод заканчивается строкой вида `Готово: установлено 7, пропущено 0 (корень: …)`. В проекте появились `.pumba/` и `.claude/`.

**2. Открываем доску**

```bash
pumba
```

Пять пустых колонок, выбран «Бэклог».

**3. Эпик и задачи**

- `N`: название «Вход в систему», `Ctrl+S`. Получился `E-001`.
- Эпик выбран, жмём `n`. Название «Форма входа». В описании пишем, что сделать и как проверить, и ссылку на файл через `@` (например, `@src/login.html`). Поле «Эпик» уже заполнено, `Ctrl+S`. Получился `T-001`.
- Ещё `n`: «Проверка e-mail на сервере». В поле «Зависит от» начинаем вводить `T-0`, выбираем `T-001` из подсказки. `Ctrl+S`. Это `T-002`: у неё метка `⊘ T-001`, у `T-001` метка `→ T-002`.
- Выбираем `T-001` и жмём `p`, чтобы положить в текущий спринт.

Файл карточки выглядит так:

```markdown
---
id: T-001
type: task
title: Форма входа
column: backlog
parent: E-001
model: default
effort: default
sprint: 1
hidden: false
order: 1
---

Сделать страницу входа с полями e-mail и пароль.

Где: @src/login.html

Критерии приёмки:
- пустая форма не отправляется;
- ошибка показывается под полем.
```

**4. Просим агента**

Запускаем Claude Code в папке `shop` и пишем: «выполни задачу T-002». Агент читает зависимости, видит, что `T-001` в «Бэклоге», отказывается и просит сначала заняться ею. Это правило сильнее любой просьбы.

Пишем: «выполни задачу T-001».

1. Карточка в «Бэклоге». «Перед работой» велит предупредить и спросить. Агент говорит: «Задача в бэклоге. Брать в работу?» Отвечаем «да».
2. Агент меняет `column: backlog` на `column: in-progress`. Мы видим, как карточка переехала в программе: она сама перечитывает файлы.
3. В «В работе» запускается `pumba-planner`, который составляет план. Правило «Автономность: Сначала спрашивать»: если план помечен «Крупное изменение: да», агент показывает его и ждёт подтверждения. Затем `pumba-tester` пишет тесты (правило «Тесты обязательны»), `pumba-worker` реализует, агент сам запускает проверки.
4. Проверки зелёные, карточка переезжает в «На ревью». `pumba-reviewer` смотрит дифф. Если есть замечания «блокирует» или «стоит поправить», карточка возвращается в «В работе», и замечания дословно уходят исполнителю.
5. Ревью одобрило: `pumba-committer` делает один коммит по правилу «Conventional Commits», карточка переезжает в «Готово».
6. Агент пишет отчёт: коммит, ветка (`pumba/T-001-login-form`), результат проверок и «разблокируется `T-002`: все зависимости в последней колонке».

В теле `T-001` в разделе `## Ход работы` остались строки с переносами.

**5. Дальше**

Теперь `T-002` не заблокирована. «Выполни задачу T-002» пройдёт тот же путь. Когда все дочерние карточки эпика в «Готово», у `E-001` на доске полная шкала прогресса `▰▰▰▰ 2/2`.

Если на любом шаге агент не справился или ждёт решения, карточка окажется в «Ждёт разработчика». Причина записана в «Ходе работы». Решите вопрос, напишите агенту «продолжи T-001», и он вернёт карточку в «В работе».

## 11. Структура `.pumba/`

```
.pumba/
  board.json
  AGENTS.md
  tasks/
    E-001.md
    T-001.md
    T-002.md
```

### `board.json`

| Ключ | Что хранит |
|---|---|
| `version` | версия формата (1) |
| `columns` | колонки по порядку: `id`, `name`, `color`, `agent`, `next`, `before`, `rule`, `after` |
| `models`, `efforts` | списки моделей и уровней размышления для форм |
| `default_model`, `default_effort` | значения по умолчанию для новых карточек |
| `sprint` | номер текущего спринта |
| `rules` | шесть правил проекта: `id`, `title`, выбранный `value` и варианты `options` |
| `custom_rules` | «Свои правила» (Markdown) |
| `tools` | id инструментов, для которых ставился набор |

Колонка со всеми полями:

```json
{
  "id": "in-progress",
  "name": "В работе",
  "color": "orange",
  "agent": "pumba-worker",
  "next": "review",
  "before": "…",
  "rule": "…",
  "after": "…"
}
```

Цвета: `purple`, `orange`, `green`, `red`, `pink`, `tan`. Последняя колонка в списке завершающая. Старый `board.json` без новых ключей читается как есть.

Если `board.json` не читается, программа ничего не записывает и сообщает об ошибке: файл не будет перезаписан.

### `tasks/<ID>.md`

Файл начинается блоком `---` с ключами в таком порядке:

| Ключ | Значение |
|---|---|
| `id` | как имя файла |
| `type` | `task` или `epic` |
| `title` | название одной строкой |
| `column` | `id` колонки из `board.json` |
| `parent` | id эпика (пишется, только если есть) |
| `model`, `effort` | подсказки агенту, `default` если без предпочтений |
| `sprint` | номер спринта (пишется, только если есть) |
| `hidden` | `true` или `false` |
| `order` | позиция в колонке |
| `depends` | id через запятую (пишется, только если есть) |
| `deleted`, `deleted_at` | корзина: пишутся, только если карточка в корзине |

После закрывающего `---` идёт пустая строка и тело в Markdown. Id берётся из имени файла. Ссылки `@путь` считаются от корня проекта.

Важные детали:

- pumba сам пишет frontmatter и выбрасывает незнакомые ключи, поэтому агенты их не добавляют;
- кодировка UTF-8, переводы строк `
`; BOM и CRLF программа при чтении терпит, но агентам велено писать без BOM;
- нечитаемые карточки не пропадают молча: имена файлов показываются красным в строке состояния;
- программа отслеживает изменения на диске и сливает их с вашими правками: если агент дописал «Ход работы» или перенёс карточку, а вы в этот момент ничего в ней не меняли, внешняя правка сохраняется.

### `AGENTS.md`

Создаётся и переписывается программой. Подробности в [разделе 7](#7-правила-проекта-и-pumbaagentsmd). Это единственный файл, который агенты читают первым.

## 12. Частые вопросы

**Нужно ли коммитить `.pumba/`?** Решаете вы. Это обычные текстовые файлы, git их видит. В `.gitignore` проекта их стоит добавлять, только если доска нужна лично вам.

**Агент не видит скилл или субагента.** Проверьте, что набор поставлен для вашего инструмента: `pumba install --tools <id>`. В конце вывода должны быть строки «установлен» или «пропущен». Если сессия агента была открыта до установки, откройте новую.

**Агент отказывается брать карточку.** Скорее всего, она заблокирована: хотя бы одна зависимость не в последней колонке. Агент перечислит блокирующие карточки. Либо доведите их до конца, либо уберите зависимость в форме правки (`Enter`, поле «Зависит от»).

**Агент остановился на «Бэклоге».** Так задано правилом «Перед работой» у колонки: он ждёт ответа «да». Либо ответьте, либо перенесите карточку в «В работе» сами (`L`).

**Хочу сам проверять результат перед «Готово».** Очистите «После успеха» у «На ревью» и уберите коммит из её «После работы»: агент остановится после ревью, а коммит и перенос сделаете вы.

**Хочу, чтобы агент не трогал `.pumba/`.** Выберите правило «Обновление доски: Вручную». Тогда агент предлагает перенос и ждёт вашего «да».

**Можно ли добавить свою колонку, например «Тесты»?** Да: `c`, заполните название, три части правила, исполнителя и «После успеха». Колонка встанет перед «Готово». Чтобы карточки в неё приходили, укажите её как «После успеха» у предыдущей колонки.

**Что будет с карточками при удалении колонки?** Они перейдут в первую из оставшихся колонок, ссылки `next` на удалённую колонку очистятся. Первую и последнюю колонки удалить нельзя.

**Почему карточка оказалась в первой колонке и помечена `?колонка`?** В её файле `column:` указан несуществующий `id` (опечатка или удалённая колонка). Откройте карточку клавишей `Enter` и нажмите `H`/`L` или поправьте строку в файле.

**Как восстановить удалённую карточку?** `B`, выберите карточку, `Enter`.

**Работает ли русская раскладка?** Да, клавиши распознаются и в ЙЦУКЕН.

**Где посмотреть справку по клавишам?** `?` на доске. Внутри форм: `Ctrl+S` сохранить, `Esc` отмена.

**Почему имена моделей `opus`, `sonnet`, `haiku`, а у меня другой инструмент?** Это подсказки для агента. Списки можно изменить клавишей `M`. В не-Claude-инструментах скилл читает их как уровни сложности (подробности в разделе 3 скилла `pumba-task` вашего пакета).

**Что в `templates/`?** Исходники набора для агентов: агенты, скиллы и пакеты под разные инструменты. Они вшиты в бинарник, и после установки папка `templates/` программе не нужна. Описание: [`templates/README.md`](templates/README.md), [`templates/targets/README.md`](templates/targets/README.md), исследование форматов инструментов: [`templates/TARGETS.md`](templates/TARGETS.md), набросок будущего API для агентов: [`templates/API-DESIGN.md`](templates/API-DESIGN.md).
